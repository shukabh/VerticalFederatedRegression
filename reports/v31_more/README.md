# Follow-up checks: coverage on real data, the coverage repeat, 100+ encrypted runs, full-record SSP cost

Paper check items #27, #30, #31 and #34 (`grep -n tocheck paper/main.tex`). Protocol v3.1, delta = 1e-9, settings from
`implementation/vfr/dp.py` `SETTINGS` (I: exact r_1, f_1 = 0.25, theta* = 2.5, intervals; P: theta* = 1.5,
alpha_L = 0.75, f_1 = 0.25, no intervals; previous setting: f_1 = 0.1, union-bound radius). Target of the Wald interval
for theta_lambda: 1 - alpha_CI = 0.955 per coefficient. No encrypted run used a register above 16,384 rows; nothing ran at
100k-1M rows.

Confidence intervals. Coefficients of one release share its noise, so pooled coverage is not a binomial count. Every
pooled coverage below has a **release-clustered** 95% interval (normal approximation on the per-release coverage
fractions, which are i.i.d. for fixed data); the naive Wilson interval is also in the JSON. Design effects are 1.0-2.1.

Full numbers: `key_numbers.md` (generated by `experiments/v31_more/tables_more.py`). Draft paper text:
`paper/drafts/more.tex`. Figures: `paper/figures/{coverage_real,coverage_repeat,noise}_more.png`.

## #27 Coverage on real data with calibrated noise (`coverage_real.json`)

Setting I, sigma_1 and sigma_2 from the implementation's Calibrate at delta = 1e-9 and eps in {1, 4, 8} (kappa 40/44/48),
block normalization with the fold-0 reference rows (as in 13.7-13.8), plaintext simulation of the full mechanism
(stage 1, stage 2, gate, `solve.stage2_infer` with 2,000 antithetic bootstrap pairs). **Fixed data**: the cohort is the
first n matched rows of fold 0 (or all of them), so theta_lambda is a fixed function of the data and each release's
lambda; **1,000 releases per cell**, 48 cells.

* Datasets: protein and the other sweep datasets (bike, elevators, pol). Block normalization keeps the ridge on in every
  release there at every size the data allow (protein's n_off is about 80k-560k for eps = 8 to 1; bike's and elevators' block-normalized
  designs are singular). 3droad (p = 4) was added so that the ridge-off regime is also checked on real data (ridge off
  from n = 1,000 at eps >= 4 and n = 5,000 at eps = 1).
* **Wald coverage of theta_lambda: 0.945-0.964 over the 48 cells** (per coefficient 0.935-0.979); 0.952-0.964 in the 40
  ridge-on cells and 0.945-0.961 in the 8 ridge-off cells. The gate refused no release.
* **Protein: 0.952-0.963** in all 12 cells (n = 1k, 5k, 20k, 36,584; eps = 1, 4, 8); lowest 0.952 (0.947-0.958) and
  0.953 (0.947-0.959) at eps = 8, n = 20k and 36,584; every protein interval contains 0.955 or lies above it.
* The ridge-on cells lean conservative: 26 of 48 clustered intervals lie above 0.955 (elevators 0.959-0.964, bike and
  pol at small n). One interval lies below: 3droad, n = 25k, eps = 1, 0.945 (0.937-0.952). Re-run with 5,000 fresh
  releases (`coverage_real.py recheck`, `coverage_real_recheck.json`) it gave **0.9554 (0.952-0.959)**; the first value
  was a fluctuation (one of 48 cells).
* Coverage of beta. The paper uses the least-squares fit on all non-reference rows as the reference coefficient on real
  data (FWS comparison, Table tab:fws_real), so the bias-aware interval's coverage of that fit is recorded, but with fixed
  data it is coverage **conditional on one sample** and not the interval's guarantee (which is over sampling and noise
  together): when the mechanism noise is small against the sampling error, each coefficient is covered in nearly all
  releases or nearly none. The interval is unbounded wherever L_hat = 0, i.e. in every ridge-on cell except protein at
  n >= 20k, eps = 8 and n = 36,584, eps = 4 (finite, covers 1.000). On 3droad (ridge off): 0.952-0.989 at n <= 5k, and
  0.85, 0.67, 0.67 at n = 25k (two of the three slopes covered in almost every release, the third rarely) - which shows
  that a fixed-cohort check says nothing about the beta interval. Coverage of beta needs resampled cohorts, as in the
  FWS real-data table.

previous setting, data rebuilt with the same code and seeds, the noise s.d. the encrypted runs used, Bboot = 2,000;
**10,000 releases per setting**.

|---|---|---|---|---|

| synthetic, ridge off | 8 (48) | **0.9554 (0.9540-0.9567)** | 204/220 = 0.927 (0.885-0.955) | 0.053 |
| protein standardize | 1 (40) | 0.9562 (0.9549-0.9575) | 50/50 | 1.00 |
| protein standardize | 4 (40) | 0.9561 (0.9547-0.9574) | 49/50 | 0.88 |

| protein block norm | 1 (40) | 0.9577 (0.9563-0.9591) | 47/50 | 0.36 |

* **Coverage meets 0.955 at eps = 8 (0.9554) and in every protein setting (0.9548-0.9577)**; every per-coefficient value
  is 0.951-0.963, no coefficient is significantly below target, and the standardized errors have s.d. 0.991-1.002.
* The earlier encrypted counts are what batches of 20 (or 5) runs give: the probability that a plaintext batch of the
  same size covers no more is 0.05-1.00. Pooled, the earlier encrypted runs covered 699/740 = 0.945 against 707.4
  expected (sd 6.1): z = -1.39, one-sided p = 0.08.

## #31 Encrypted runs (`encrypted_more.json`, `encrypted_more_first50.json`, `encrypted_more_noise.npz`)

Full OpenFHE protocol (two processes, OPRF + labeled PSI, threshold CKKS, exact discrete-Gaussian noise in O's share),
synthetic dataset of the earlier checks: n = 10,000 matched, register 12,000 rows padded to **16,384**, cohort 11,000,
seed 11, delta = 1e-9. **Implementation at commit f30b025** ("Implementation: reject a PSI output with a repeated
position ..."); the first 50 runs of each configuration ran with HEAD = f30b025, the rest with HEAD = 77fa220, a
paper-only commit (no file under implementation/ changed). Median 21-23 s per run (29 s for the replication, three runs
in parallel). 550 encrypted runs in total.

Configurations: **I2** (setting I, eps = 2, ridge on), **P1** (setting P, eps = 1, ridge on), **I8** (setting I,
eps = 8, ridge off: n_off of the matched design 3.9k). Specified as about 50 runs each; since runs took about 20 s, all
three were extended to 100 (after a look at the first 22-26 runs only). Because I2's 100 runs came out low (below), a
**replication I2r** of 150 more I2 runs with fresh seeds followed, reported separately.

| | I2 (100) | I2r (150) | P1 (100) | I8 (100) |
|---|---|---|---|---|
| lambda in plaintext 95% range | 95/100 | 144/150 | 92/100 | 100/100 (all 0) |
| theta in plaintext 95% range | 1034/1100 = 0.940 | 1575/1650 = 0.955 | 1038/1100 = 0.944 | 1053/1100 = 0.957 |
| s.d. of z vs simulated theta given lambda | 1.043 | 0.999 | 1.018 | 1.013 |
| Wald coverage of theta_lambda | **1037/1100 = 0.943** (0.928-0.958) | **1586/1650 = 0.961** (0.953-0.970) | (no intervals) | **1054/1100 = 0.958** (0.945-0.971) |
| plaintext coverage, same configuration (10,000 releases) | 0.9585 (0.9573-0.9597) | same | | 0.9555 (0.9542-0.9568) |

* No release was refused, A was exact in every run, and feeding each run's decrypted releases (rebuilt from the
  recorded noise) to the plaintext solver with the run's seed reproduced lambda, the estimate and the half-widths to
  better than 1e-11 (relative). So an encrypted run differs from a plaintext one only through the law of its noise.
* I2's 100 runs covered 1,037 of 1,100, just below the 2.5% quantile (1,040) of 100-run batches of the plaintext
  mechanism; its first 50 covered 516/550 (plaintext 2.5% quantile 517). The replication covered 1,586/1,650 = 0.961,
  and I2 + I2r pooled 2,623/2,750 = **0.954 (0.946-0.962)**. I8 (ridge off) covered 0.958. With the noise tests below,
  this puts I2's shortfall down to chance (it was the worst of four batch-level comparisons).
* **Noise.** Released entries standardized by the calibrated sigma (stage 1: the 51 O-dependent entries of G; stage 2:
  those 51, the 11 of c and y'y). Pooled over the 450 runs of all configurations, per release type:
  * **release 1: 22,950 entries, mean +0.0055 (SE 0.0066), s.d. 0.995, KS p = 0.13** against the calibrated law;
  * **release 2: 27,900 entries, mean +0.0043 (SE 0.0060), s.d. 1.006, KS p = 0.48**;
  * per configuration and release type every mean is within 1.9 SE of zero (largest: I2 release 1, +0.026, run-level
    p = 0.03, KS p = 0.03; its replication I2r gave -0.0006);
  * the slots outside the packed entries carry the same noise on a plaintext 0: about 16,000 values per release,
    **1.6-2.4 million per configuration and release**; their mean is within 0.0011 of zero (SE 0.0006-0.0008) and their
    s.d. 0.9992-1.0008 in every configuration, and the s.d. of the per-release s.d. matches its sampling value (0.005-0.006),
    so the noise scale is right release by release. Over all 14.7 million slot values of the 550 runs the mean is
    -0.0004 (SE 0.0003).
  * The earlier spot checks' means (-0.17 on I's release 1, 255 entries; -0.10 under P, 565 entries) are **not
    reproduced**: the same configurations now give +0.026 (I2, 5,100 entries), -0.0006 (I2r, 7,650) and +0.006 / -0.003
    (P1). With the earlier runs included the pooled means are +0.003 (release 1, 23,715 entries) and +0.004 (release 2,
    28,830). **Verdict: the slightly negative means were sampling fluctuations; the noise mean is zero to within 0.01
    sigma on the entries and 0.002 sigma on all slots.**
* The calibrated law. The released slot noise is the canonical embedding of an exact discrete Gaussian on the
  coefficient lattice (log2 sigma_c about 60), so its law in a slot is N(0, sigma_slot^2) to far better than any KS test
  here resolves; the KS tests are against that law with the calibrated sigma_slot.

## #34 Cryptographic cost of full-record SSP (`cost_fullrecord.json`)

From the implementation's cost model (`implementation/bench/cost_model.py`, per-operation costs measured by
`bench_micro.py`, single thread, N = 2^14, d_R = 4, d_O = 6, n_R^max = 2,000). Full-record SSP releases triu A without
the constant n: (d_R + 1)(d_R + 2)/2 - 1 = **14 more entries per release** at d_R = 4 (the check item's d_R(d_R+1)/2 = 10
omits the four intercept-row sums). In the protocol's architecture the 4 sums use R's existing uploads b * x_j and the 10
products need **10 more encrypted upload vectors** b * x_j * x_k from R (O multiplies by a vector of ones).

| register rows | m | aggregation, v3.1 -> extra | O CPU, v3.1 -> extra | R CPU extra | communication, v3.1 -> extra | single-thread wall (est.) |
|---|---|---|---|---|---|---|
| 4,096 | 1 | 16.3 s + 3.6 s (x1.22) | 21.5 s + 3.7 s (x1.17) | +0.2 s | 48 MB + 5 MB (x1.10) | x1.16 |
| 16,384 | 2 | 17.0 s + 3.8 s (x1.22) | 25.4 s + 3.9 s (x1.15) | +0.4 s | 53 MB + 10 MB (x1.19) | x1.16 |
| 65,536 | 8 | 21.3 s + 4.7 s (x1.22) | 40.9 s + 5.3 s (x1.13) | +1.6 s | 73 MB + 40 MB (x1.55) | x1.16 |

* Aggregation grows by 77/63 = 1.22 (one EvalSum and m multiply-adds per entry; with one cached all-ones plaintext the
  encode cost of the new entries vanishes: x1.17-1.21). The upload grows by 10/6 vectors, which dominates the extra
  communication at 64k rows (+40 MB).
* **The releases cost the same**: each is one ciphertext whose noise is sampled per ring coefficient, and 65 / 77
  entries fit in the 8,192 slots as 51 / 63 do. Calibrate with the larger entry counts: log2 B_tot +0.15-0.18,
  log2 Omega_f 62.63 -> 62.78, same kappa, same sigma (to 1e-11). (The U-side bound of the new vectors,
  |b x_j x_k| <= B_R^2, enters B_tot's derivation and was not re-derived.)
* The cost model over-predicts the measured aggregation by 8-16% at these sizes, so the absolute seconds are slightly
  high; the ratios are exact under the model. A secure-aggregation protocol of another kind (Karr et al., Gascon et al.)
  would have its own cost, not modelled.
